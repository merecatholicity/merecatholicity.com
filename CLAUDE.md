# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This file is about how the **website and its infrastructure** work: the GitHub Pages side, the Cloudflare Workers/D1/R2 side, and the build system that ties them together.

If you are working on any text-based content and `CONTEXT_DUMP.txt` is present in the repo root, ingest it first. This file stays focused on infra.

**Never store sensitive information in this file** (or anywhere committed): no API tokens, secrets, private keys, or unpublished credentials. Cloudflare Worker secrets are set with `wrangler secret put`, not in source. The identity hashes and Turnstile sitekeys that do appear in the repo are public by design.

**Keep this file current.** When infrastructure changes in an important way — a hosting or DNS pivot, a new or retired Worker, a change to how builds or deploys run, a plan or quota policy change — update this file in the same change.

## Hosting and delivery

- **GitHub Pages** serves the repo root directly. The site is static: every `*.html`, PDF, image, and built artifact is committed and served as-is. `CNAME` points Pages at the apex domain.
- **Cloudflare** fronts Pages as a proxy (DNS + CDN + edge features). Do not change the SSL mode to Full (strict); the working configuration is deliberate.
- Because the site is prebuilt static files, "deploying" the site is just committing and pushing built output. There is no site build step on the server.
- **Cache-busting `comments.js`.** The client is included as `comments.js?v=NN` in every commented page (currently 9 includes); bump `NN` with one `sed` across all of them on any `comments.js` change, or Cloudflare serves the stale script. Cloudflare caches each `?v=N` URL independently and treats it as immutable, so **do not fetch a freshly-bumped `?v=N` URL until GitHub Pages has finished deploying the new file** — a probe mid-deploy freezes the OLD bytes under the new key, and the only clean recovery is to bump again to an unpolluted number. To test origin freshness without polluting a real key, fetch a throwaway query string (`comments.js?probe123`), which always misses cache and hits origin. **Confirming the Pages deploy actually landed is optional and usually unnecessary** — pushing the bump is the end of a normal `comments.js` change. Only poll a throwaway `?probe` for a marker from the new bytes when you genuinely need the new client live before a next step (followup headless testing against the live site, or reproducing a bug on prod). With no such followup, there is nothing to wait for, so don't burn turns watching the deploy. `style.css` is unversioned, so CSS changes propagate on Cloudflare's cache TTL rather than instantly.

## Build system

Builds are pinned to `SOURCE_DATE_EPOCH=1784160000` so rebuilds are byte-identical and git only churns when text actually changes. Built artifacts are committed.

- `./build-confession.sh` — book PDF (`Mere_Catholicity.pdf`) via pdflatex (run twice for refs/TOC).
- `make html` — HTML editions (`book.html`, `bishop-presbyter.html`) via pandoc, plus resources pages, then runs the link check.
- `make publish` — KDP paperback PDF (same `confession.tex`, `\PAPERBACK` flag, separate jobname).
- `make logos` — Logos/Verbum `.docx`.
- `make menu` — regenerate all site navigation from `nav.yml`, then rebuild html.
- `make check` — `python linkcheck.py`; verifies every internal href/src and `#fragment` on the site resolves. This is the only automated test.
- `make chart-pdfs` — print chart pages to PDF with headless `/usr/bin/chromium` (note: `~/bin/chromium` is an emacs wrapper, not a browser).
- `make serve` — local server on port 8000.
- `make comments-backup` — export the live D1 comments DB to `comments-backup.sql` (kept out of git).

**Navigation** is generated: `nav.yml` is the single source. `nav.py` renders `nav.html` and rewrites the inline nav block in every page listed in the `PAGES` array at the top of `nav.py`. A new site page must be added to that list or `make menu` will not touch it.

**Resources** (`resources/`) are public-domain texts rebuilt as our own LaTeX. `*2tex.py` scripts convert preserved sources into `*-body.tex`; the `WORKS` list in `resources/Makefile` maps each source to its published root PDF, and outputs land in the repo root so Pages serves them.

## Verifying the live site (headless browser)

`make check` (linkcheck) is the only static test. Anything that depends on **client JS actually running** — anchor jumps, pagination-aware scroll-to-comment, board/DM rendering — cannot be verified with curl, only with a real browser. A headless Chromium is preinstalled at `~/.cloakbrowser`: several `chromium-<version>/` dirs, each holding a matching `chrome` and `chromedriver`. There is no node/npm, so drive it through chromedriver's WebDriver HTTP API using Python stdlib only:

- Launch `~/.cloakbrowser/chromium-<ver>/chromedriver --port=N` in the background; poll `GET /status` until ready.
- `POST /session` with `capabilities.alwaysMatch.goog:chromeOptions.binary` set to the sibling `chrome`, args `--headless=new --no-sandbox --disable-gpu --disable-dev-shm-usage --window-size=1200,800 --user-data-dir=<scratchpad>`. Pair `chrome` and `chromedriver` from the **same** version dir or the session refuses to start.
- `POST /session/<id>/url` to navigate (full URL including the `#comment-N` hash), then poll `POST /session/<id>/execute/sync` running a JS probe until the async board fetch has rendered, and read back DOM facts (element presence, `.board-pages strong` = active page, `window.scrollY`, `getBoundingClientRect().top`).
- Always `DELETE /session/<id>` and SIGTERM chromedriver when done.

This catches what curl cannot: e.g. that `community.html?topic=<t>#comment-<id>` resolves to the correct page and scrolls to the comment. (The client sends `&find=<id>` only when there is no explicit `&p`; the worker then counts prior live replies to compute the page. A bare `Math.max(1, …)` default for the page number silently disables this — the page defaults to 1 and the jump strands on page one.)

## Cloudflare Workers (dynamic backend)

The static site delegates its two dynamic features to Workers. Both are **free-tier only** — any new worker feature must stay within Cloudflare's free plan. Deploy each from its own directory with `deno run -A npm:wrangler deploy` (wrangler runs through deno; there is no npm/node setup). Config is in each directory's `wrangler.jsonc`.

- **`comments-worker/`** — the comments backend. Routed on the zone at `/api/comments*`, so it is same-origin with the pages (no CORS). Uses **D1** for storage, **Turnstile** as the spam gate, **Workers AI** (Llama Guard) for screening (`MODERATION_MODE` var), rate-limit bindings for per-IP throttles, and a monthly cron that dumps D1 to **R2** (`merecatholicity-backups`, 90-day retention). Client side is `comments.js`; a page opts in with `<section class="comments" data-comments>` plus the script (the book edition gets it via `book-tail.html`). Identity is a browser-generated key; the server stores only its SHA-256 and derives a pseudonym from the hash. NOTE: the pseudonym/reserved wordlists — and the faith-declaration codes (the `FAITHS` list in the worker, the `FAITH` label map and `FAITH_ORDER` in the client) — are duplicated in `comments.js` and `comments-worker/src/index.js` and must stay identical. Every member picks a faith (`nicene` / `indo-european` / `seeker`) at signup; it lives on the `profiles` row, is filled from the first post (fill-only, never overwriting an edited value), is changed in the profile editor, and shows under the author's name on posts and on the profile.
- **Moderation is all in-platform** (the comments worker sends no email at all now; the old signed-link moderation emails are gone, and its only remaining secret is `TURNSTILE_SECRET`). Admin powers live in the per-comment user-fingerprint dropdown: **lock/unlock** an identity (reversible; a locked hash is logged out and refused every keyed call), **delete user and all posts** (soft-deletes their comments, removes profile+avatar, and locks the hash), and **ban IPs** (every address known for the identity, each bannable alone or all at once behind a confirm that flags a shared/CGNAT v4). A `blockedReason()` gate on every keyed endpoint (writes + the DM unread poll) returns `{blocked}`, and the client logs the user out and redirects to `terms.html` where `flash.js` shows a non-fading banner. Public/cached reads are never gated. Three D1 tables: `locks` (hash), `ip_bans` (normalized IP key), and `identity_ips` (every IP behind an identity — **not a ledger**: the drawer shows only the last 14 days (`IP_SHOW_DAYS`), the monthly backup cron deletes unbanned rows idle past 30 days (`IP_KEEP_DAYS`, via `pruneIdentityIps`, first of the maintenance prunes that run before `runBackup`), and banned keys are exempt from both so a standing ban keeps its drawer handle). **Dual-stack IP capture:** a browser reaches Cloudflare on only one address family, so at post time `comments.js` best-effort fetches the other from `ipv4/ipv6.icanhazip.com` (Cloudflare-run, CORS-open; both added to the CSP `connect-src`, which is a **report-only edge rule not in the repo** — a Response-Header Transform Rule in the Cloudflare dashboard) and sends both; the worker's `recordIps()` stores the verified connection IP (`seen`) and the reported opposite-family IP (`claimed`). `ipKey()` normalizes before store and match — v4 verbatim, v6 folded to its `/64` (a client's v6 interface id rotates daily, the delegated /64 does not) — so `blockedReason` and every ban match on the /64, and neither the fallback family nor a rotated address evades a ban. The `/ipban` endpoint takes an array (ban-all); the drawer reverse-DNSes each shown IP via the admin-only `/api/comments/rdns` (Cloudflare DoH, lazy on drawer-open). Admin-only pages: the **Activity audit**, now a **moderation console** in three actionable sections under a count summary of what is waiting — **Reported** (member-flagged posts, most-reported first, each with **Dismiss**/**Delete**/a lazy author-drawer and the full topic corner when it is a topic head), **Pending review** (Approve/Delete AI-held comments, the replacement for the old email approve link), and **Recent activity** (the last 14 days across pages/book/forums, every row now carrying delete + a lazy author drawer + the topic corner for a topic) — plus the **IP ban list** (`?ipbans=1`, manual add/remove). **Reporting** is community-assisted moderation: a `reports` table (`UNIQUE(comment_id, reporter_hash)` — one flag per member), a member `report` link on every post (not your own, not shown to admins who act directly), `POST /report` (keyed, `blockedReason`-gated, POST_LIMIT'd, validates the post is `live`) that **never changes the post's status** — anti-brigade, a report only surfaces a post, it never hides it — and admin-only `POST /report/dismiss` that clears a post's flags without touching the post. The per-row topic controls (Move + sticky/lock/delete) are one `topicAdminCorner()` client helper shared by the category listing and the console, so a topic is governed identically in both. The legacy `bans` table is still checked but no longer written. Each topic on a category listing also carries admin **lock/unlock**, **delete**, and **pin/unpin (sticky)** links via the `/moderate` endpoint (act `sticky`/`unsticky`); a pinned topic sorts above the rest of its category (a `sticky` column on `comments`, `ORDER BY COALESCE(sticky,0) DESC, last DESC`) and wears a maroon `(sticky)` mark in the list and at its head. A **Move** dropdown in that same corner sends a topic — and all its replies, which each carry their own `page` — to another category via the admin-only `/move` endpoint (`UPDATE comments SET page WHERE id=? OR parent_id=?`), then DMs the original poster an automated notice, from the moving admin and delivered unheld, with a link to its new home. Board counts are computed live from `page`, so a move touches nothing else.
- **Direct messages** ride the same worker: strictly 1v1 threads in D1 (`dm_threads`/`dms`/`dm_blocks`, canonical-pair unique row, denormalized unread state), POST-with-key only (private; no admin visibility by design), Turnstile-gated sends, and shadow-blocks: a blocked sender's messages read as delivered to them but are stored `held`, invisible to the recipient, and an unblock releases them all with their original timestamps. A member may **delete a conversation** (`/dm/delete`, from an inbox row or the open thread): per-side `a_cleared_at`/`b_cleared_at` stamps on `dm_threads` (NULL = never cleared, so preexisting threads are untouched) hide everything up to the delete from that side alone — a **fresh start**, so a later message from the other reappears showing only what came after — and once both sides have cleared with no word past the earlier stamp, the thread and every `dms` row are purged outright (no FK cascade, so both are deleted explicitly). Every read path (`handleDmThreads`/`handleDmThread`/`handleDmUnread`) filters on the viewer's clear stamp. An automated move-notice is sent via `sendSystemDm` (the un-gated, always-unheld core of a DM send). Client: Inbox at `community.html?inbox=1`, threads at `?dm=<hash>`, unread badge by the Logout links throttled by a 90-second localStorage cache, and a member autocomplete fed by one cacheable `/dm/directory` fetch with all fuzzy matching done client-side.
- **In-app notifications** ride the same worker — the retention backbone now that email is gone — reusing the DM unread machinery. Two D1 tables: `notifications` (one row per event for one recipient: `kind` `reply`/`mention`, `topic_id`/`comment_id` to jump to, `actor_hash`, `read_at` NULL = unread, the DM stamp idiom; index on `(recipient_hash, id)`) and `watches` (`PRIMARY KEY (hash, topic_id)`). `deliverNotifications()` runs in `handlePost`'s `ctx.waitUntil` **only for a `live` board post** (a held/pending post notifies no one, though the author still auto-watches): the author **auto-watches** the thread (topic or reply), each client-supplied `mentions` hash (validated 64-hex, capped at 10) gets a `mention`, and a reply **fans out** to the topic author and every watcher save the replier and anyone already mentioned — one dedup'd `db.batch`; `handlePost`'s reply SELECT was widened to pull the topic `author_hash`. @mention resolution is **the same `/dm/directory` + `dmScore` fuzzy search as DM send**, sprung by an `@` token in the reply box (`attachMentions`) and carrying the picked member's own hash so a one-way pseudonym is never reversed; `boardPost` sends the `mentions` whose token still stands in the body. Keyed POST endpoints, all `blockedReason`-gated like the DM ones: `/notifications/unread` (badge count via the 90-second-cached `notifUnreadCheck`, a Notifications link beside the Inbox in `renderIdentity`), `/notifications` (list at `community.html?notifications=1` = `viewNotifications`, each row linking `?topic=T#comment-C`), `/notifications/read` (opening the list stamps all read), and `/watch` (`act` `status`/`watch`/`unwatch`, the manual toggle in the topic header). The kind codes `reply`/`mention` are a server `CHECK` plus a client label map — keep them in step. `pruneNotifications` joins the cron chain (below): read rows past `NOTIFICATIONS_KEEP_DAYS` (30) go, plus any notification whose post is gone or watch whose thread is gone; unread rows are kept however old.
- **Unread threads, mute, and profile post-history** ride the same worker (a retention/UX trio). **New since last visit:** a `thread_reads` table (`PRIMARY KEY (hash, topic_id)`; `topic_id = 0` is a per-user *read-all floor* set lazily on the first `/board/unread` call, so a newcomer starts all-read instead of facing a wall of "new") drives four keyed, `blockedReason`-gated POSTs — `/board/unread` (total + per-category new counts; a topic is new when its `last_at` beats the reader's per-thread `read_at`, or the floor), `/board/reads` (the unread topic ids for one category, so `viewCat` marks them `● new`), `/board/read` (upsert `read_at=now` on opening a topic), and `/board/read-all` (reset the floor to now and drop the now-redundant per-thread rows — the **Mark all read** action on the board index). **Mute** is purely client-side (an `mc-muted` localStorage hash list; `isMuted`/`toggleMute`): a muted member's in-thread posts collapse to a *show* placeholder, toggled from the post head or the profile — no server call, orthogonal to the DM shadow-block. **Post-history:** `GET /board/author?hash=&p=` (READ_LIMIT, `cacheHeader`) returns a member's own live forum posts, newest-first and paginated, rendered as a **Recent posts** list on their profile — deferred behind a *Show recent posts* link so a profile view makes no post-history call until the reader asks (a worker-load saving).
- **Profiles and avatars** ride the same worker. Profiles (nick/bio/signature) live in the D1 `profiles` table, AI-screened like comments. Avatars are 400x400 JPEG only, 500 KB cap, magic-byte-sniffed server side, screened by a Workers AI vision model (LLaVA), and stored in R2 **`merecatholicity-avatars`** under one fixed key per identity (upload = overwrite, so no orphans). The monthly backup cron dumps the whole database schema-agnostically — excluding the search index's FTS5 shadow tables (`comments_fts%`, derived data) but appending its virtual table, triggers, and a `('rebuild')` so the one file restores search on its own — and mirrors the avatar objects into the backups bucket; **any new state store outside D1 must be added to `runBackup()`'s mirror or it is not backed up**. A mid-month snapshot can be forced through the admin-keyed `POST /api/comments/backup`. Before each dump the cron runs a housekeeping chain — `pruneIdentityIps` → `pruneComments` → `sweepDms` → `pruneNotifications` → `runBackup` — that also hard-removes soft-deleted comments older than 30 days (`DELETED_KEEP_DAYS`, since comments are only ever soft-deleted) and any live replies a topic delete left orphaned (topic delete doesn't cascade to its replies), sweeps stray DM rows (messages whose thread is gone, threads with no messages), and clears read notifications past their month, any notification/watch left pointing at a vanished post or thread, and the orphaned `thread_reads` and `reports` rows whose thread or post is gone (both swept inside `pruneNotifications`); **`pending` comments, shadow-`held` DMs, and unread notifications are deliberately left alone**, and each prune is self-contained so one failure never stops the backup. Cloudflare's CSAM Scanning Tool is enabled on the zone.
- **Forum full-text search** rides the same worker over an FTS5 **external-content** virtual table `comments_fts(title, body)` (`schema.sql`), kept in lockstep with `comments` by three `AFTER INSERT/UPDATE/DELETE` triggers (`comments_ai/ad/au`); `porter unicode61` tokenizer so "conclude" finds "concluded". The index mirrors ALL comments — the **forum-only, live-only** restriction is applied at query time (`page LIKE 'board:%' AND status = 'live' AND (parent_id IS NULL OR parent is live)`), so no conditional triggers are needed. `GET /api/comments/search` (READ_LIMIT, `cacheHeader`-cached) takes `q`, `cat` (a `BOARD_CATS` key), `author` (64-hex hash), `sort` (`new` = recency, else bm25 relevance), `p`. `buildMatch()` turns the query into a **safe** FTS5 MATCH by double-quoting every token/phrase — so `"exact phrase"` is an adjacency match and no FTS5 operator (`* - : ^ NEAR AND OR`) can be injected — and `snippet()` wraps matched terms in STX/ETX control chars (a body can never contain them, per `CONTROL_RE`) which the client splits into `<mark>` spans (never innerHTML). Client `viewSearch()` at `community.html?q=<query>` (+ `&cat=&author=&sort=&p=`, all URL-driven and shareable): a search box on the board index and a **Search** link in `renderIdentity`, a category `<select>`, an `@`-author filter reusing the DM directory + `dmScore` (`attachAuthorPicker`), highlighted result rows linking to `community.html?topic=<root>#comment-<id>`. **Only the forum is searched** — never article-page comments or the book. After creating the vtable on an existing DB, run `INSERT INTO comments_fts(comments_fts) VALUES('rebuild')` once to index prior rows; the monthly backup carries the vtable + triggers + rebuild (see the backup note above), and `pruneComments`'s hard deletes fire the delete trigger, so nothing extra is needed on the cron.
- **Emoji** are a `comments.js`-only feature — **no worker change**: bodies stay plain text and the images are static assets served by Pages. Standard Unicode emoji insert and store as characters; the two image packs (**memes** = a memes + a cat-memes pack, **pepe** = two pepe packs, all from emoji.gg, each source image optimized to a 128px **WebP** under `emoji/memes/` and `emoji/pepe/`, ~1.3 MB total) insert and store as `:shortcode:`. The renderer (`appendRich`, still createElement/textContent only, never innerHTML) turns a `:code:` into a same-origin `<img class="mc-emoji">` **only** when the code is on the `CUSTOM_EMOJI` whitelist (derived from the inline `EMOJI_PACKS`), a common `NAMED_EMOJI` alias into its character, and anything else stays literal text — so a body can never name an arbitrary image source. The full standard set (~1900, grouped, with search keywords) is generated from GitHub's **gemoji** into `emoji/emoji-data.json` and fetched **lazily** on first use, so it never rides the initial page load (the inline `STANDARD_EMOJI`/`NAMED_EMOJI` are the pre-load fallback). Three ways in, all attached to every composer through `mdEditor`: the **😊 picker** button (a tabbed, internally-scrolling panel — a search box, then Emoji/Memes/Pepe tabs, search focused on touch), the **`:` autocomplete** (the sibling of `attachMentions`: `@` picks a member, `:` picks an emoji, narrowing as you type on desktop and mobile), and hand-typed `:shortcode:`. Picker and `.mc-emoji` CSS is injected once as `<style id="mc-emoji-css">` matched to the site palette (`--rule`/`--maroon`/`--faint`), **not** added to `style.css`; the old markdown syntax legend under the toolbar was dropped. Regenerate the packs with `scratchpad/build_emoji.sh` (ImageMagick) and the data file from gemoji; the two duplicated wordlists caveat does not apply here (the standard data lives only client-side). Same-origin emoji images are unaffected by the report-only CSP.
- **`contact-worker/`** — the contact form backend on custom domain `contact-api.merecatholicity.com`. Turnstile-gated, throttled, sends to a verified Email Routing destination address. Client side is `contact.js`.
