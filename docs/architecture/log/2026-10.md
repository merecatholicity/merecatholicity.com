  With
  the edge tag's script blocked, nav.js's posted to the same 404. The beacon's source says why: it
  finds its config at `document.currentScript || document.querySelector('script[data-cf-beacon]')`,
  takes `?token=` from that element's `src`, and reports to `send.to`, else to
  `cloudflareinsights.com` only while its config carries no `version` — else relative. nav.js set
  `type = 'module'`, and a module script has no `currentScript`, so the beacon read the edge tag
  (version present → same-origin → 404), and on a page without that tag it would find no token and
  never report at all. With nav.js's tag made classic in the same browser, `__cfBeacon` read
  `{token, load: "single"}` and one POST went to `https://cloudflareinsights.com/cdn-cgi/rum`, 204,
  inside the CSP. The account's RUM site list answers `auto_install: false` with its ruleset
  `enabled: true` — the injector the earlier passages called missing is an account RUM object, not
  a zone ruleset — and `enabled` cannot be declared (it plans an update every run, `analytics.tf`),
  so
  the injection is stopped by the control Cloudflare documents as winning over every Web Analytics
  rule: `cloudflare_ruleset.config_settings`, phase `http_config_settings`, one rule `disable_rum =
  true` on every request; the zone had no configuration ruleset, so it is a create, and the plan
  showed nothing else. It touches only this zone's requests — the manual beacon reports to another

## Infrastructure as code (Terraform, 2026-09-08)

- **The gate waited in silence because its reviewer was its actor; a bot now asks by name
  (2026-10-08)** — the owner never got a notification that a Terraform apply waited at
  `terraform-production`. The environment was right (reviewer `a-schaefers`, id 26800291) and so was
  the account's notification setting: every run of `terraform.yml` and `merecat.yml` is
  `actor=a-schaefers triggering_actor=a-schaefers`, because the pushes and the dispatches ride the
  owner's own credential, and GitHub tells nobody of their own activity — the review request is one
  of those. Re-routing the runs through another identity would have touched every road; asking from
  a different one touches none. So each gated job has a sibling, `ask`, with the same `needs` and
  `if`: `scripts/ci_ask_review.sh` under the job's `GITHUB_TOKEN` polls
  `/actions/runs/{id}/pending_deployments` (up to five minutes; the gated job registers within
  seconds), takes the reviewers from the gate itself, and comments on the run's own commit with an
  @mention and the run's link. (The first cut posted to a standing issue: the repository has issues
  off, and the drill answered HTTP 410. GitHub's permissions table lists a commit comment under
  `contents: read`, but the job token was refused, 403, so the asker holds `contents: write` and is
  held by the test to a sparse checkout of its one script and one step that runs it. Turning issues
  on would have opened a public inbox to strangers.) The author is github-actions[bot], so the
  mention is somebody else's act and is delivered. A run approved before the asker looks is asked of
  nobody, and the asker never holds a secret. `EveryGateAsks` in
  `tests/py/test_pipeline_workflows.py` sweeps every job whose environment has a `reviewers` block
  in `terraform/github.tf` and fails one without its asker.
