## Build system

**Navigation robustness + PWA hardening (2026-08-02).** Born of a live report (iOS PWA white
first-add + seconds-blank hops; fast tapping stranding empty pages until a manual refresh).
**softNav is LATEST-WINS now** (`app/shell.ts`): every click starts a navigation that supersedes the
one in flight (a `navSeq` guard on every mutation + an AbortController on the fetch) — the old
`navigating` boolean preventDefault'ed then silently DROPPED every tap made during a fetch, and a
HUNG fetch (no timeout) wedged it forever, freezing all soft navigation. Document fetches ride
`fetchDoc`: 9s per-attempt timeout (armed through the body read) + 2 retries on
network/timeout/429/5xx; ANY terminal failure falls back to `location.href` — the shell never
strands a dead page. A visible **loading pill** (`.mc-navload`, safe-area-aware — the 2px progress
bar is imperceptible in iOS standalone) appears 300ms into any navigation and clears on settle. A
**failed per-page script load is no longer remembered as loaded** (it once blanked
community/feed/inbox on every later soft-nav until a hard refresh): it retries once, then clears the
flag so the next navigation tries again. **comments.js boot ordering fixed**: the old 1.5s "boot
classic anyway" fallback booted before `app.js` arrived and threw a TypeError on the Phase-5
kernel-less `window.mcCore` — static section empty, once-only flag = blank forever; it now boots
only once the kernel stands (mc-shell-ready + a 250ms poll), re-injects `app.js` once at 8s if the
bundle looks lost, retries a throwing boot (max 3), and leaves an honest reload note at 45s.
`route()` is wrapped (`routeSafe`) so a throwing view renders a Try-again note, never a silent
blank. **Store-level 429 self-heal** (`app/store.ts` fetchJson, tested in
`tests/js/store.test.mjs`): a throttled read (`/too many|slow down/i`) waits 1.6s/3.5s and re-asks
(bounded) before the refusal reaches the view — a rapid navigator gets a briefly-late render instead
of a dead "could not be loaded"; `fetchRetry` (comments.ts) gained a 15s per-attempt timeout (an
unsettled fetch was an eternal "Loading…" with no retry). **Lit views' terminal errors carry a
Try-again remount** (`retryTpl` in `app/views/util.ts`: replaces the element with a fresh instance
carrying the same wiring props, so connectedCallback re-runs the whole load; also fixed the admin
observers' `_loading` wedge that made retry impossible after one failure). **PWA**: the manifest + a
NEW `apple-touch-icon` are injected from `nav.js` (the first script every page carries) — the
runtime-late manifest (after the app.js network fetch) is what produced the white first-add web
clip; manifest `background_color` is now charcoal `#0f1113` (the launch screen painted near-white
against the charcoal-dark default). **`sw.js` is VERSION v3** with two deliberate policy changes:
(1) the six tab-destination page SKELETONS (`/`, index, community, feed, messages, profile,
merecat-ai) are cached **by pathname**, stale-while-revalidate — their live content is API-driven so
nothing dynamic is served stale, and a cold-started installed app now paints instantly instead of
seconds of network blank; all OTHER documents and `/api/*` remain network-only (the budget law
holds). (2) the unversioned `nav.js`/`style.css` are **network-first** (2.5s race, cache = offline
fallback) — SWR on them meant every post-deploy launch ran yesterday's bundle against today's markup

re-injected across all 272 pages) reveals at 2.5s (was 4s) and also when `mc-home` mounted but

**The PWA self-update architecture (2026-08-02, sw VERSION v4 — born of a live report: an installed
iOS app ran days-old code with no path to healing, and a freshly re-added one rendered tab skeletons
with no content).** Root causes, all structural: an installed app is usually RESUMED, not relaunched
— a resume fires no navigation, and a navigation was the ONLY moment iOS ever re-checked `sw.js`;
and the SW-cached tab skeletons carry their deploy's `comments.js?v=` baked into the markup, so
every post-deploy launch ran yesterday's client against today's kernel (mixed-version = the shell
paints, the content never does). Three mechanisms now stand, ALL in the two unbundled hand files
`docs/sw.js` + `docs/nav.js` (deliberately outside the bundle, so even a page running a stale
`app.js` still pumps updates): (1) **the update pump** — nav.js registers the SW
(`updateViaCache:'none'`) and calls `registration.update()` on every return-to-foreground +
`pageshow(persisted)` + an hourly tick, throttled to one check per 5 min; (2) **the stale-skeleton
heal** — sw.js revalidates every cache-served skeleton against ORIGIN (`cache:'no-cache'`; the
10-min browser HTTP cache no longer masquerades as revalidation — Pages answers 304 cheaply),
byte-compares, updates the cache, and messages the page (`mc-page-updated`); a YOUNG page (<30s old,
not mid-typing, ≤2 heals/5min, sessionStorage-deduped per cause) reloads once onto the fresh bytes —
a launch that painted yesterday's markup heals itself in ~1–2s; (3) **the update announce** — a
newly-activated SW sweeps old VERSION caches and tells every page (`mc-sw-updated`); a page BORN
CONTROLLED heal-reloads (it is living through an update), one born uncontrolled ignores it (it just
witnessed the first install — nothing it runs is stale). HARD-WON delivery lessons, each found
headless (`scratchpad/pwa_test2.py`, 6/6 against an isolated local serve): a postMessage sent right
after serving a navigation response reaches NOBODY (the new document is not yet in
`clients.matchAll()`, the dying old one is) ⇒ `tellClients` sends 4× over ~4.5s and pages dedupe;
`controllerchange` provably fails to fire on claim in some engines ⇒ never rely on it (kept only as
belt-and-braces); a page using `addEventListener('message')` on `navigator.serviceWorker` MUST call
`startMessages()` or every signal queues forever; and a pre-claim `matchAll()` from a NEW worker
lists only clients it already controls — none. Also fixed in v4: a cache+network double miss
resolved respondWith with `undefined` (a silent NetworkError the shell's retry/fallback machinery
could not classify — it now REJECTS honestly), a 5xx was served over a good cached copy (the cache
now wins), fetches re-issue by URL instead of re-dispatching the Request object (a WebKit
navigation-request trap), `cache.put` can never raise an unhandled rejection (iOS private
mode/quota), and truly `?v=`-versioned URLs skip background revalidation outright (their URL is
their freshness — refetching them doubled bandwidth). **`?debug=1` on any page** paints a diagnostic
overlay from nav.js — standalone-vs-browser mode, the versioned scripts actually running, SW
controller state, live cache VERSIONs, the last JS errors (the ring buffer records on EVERY page
from the first script, so it can be consulted after the fact), and since 2026-08-03 the **persistent
breadcrumb ring** (`window.mcCrumb`, localStorage `mc-crumbs`, cap 20 — it SURVIVES a reload, unlike
the in-page error ring): every real unload leaves a `pagehide` crumb, every heal-reload names its
cause, every swallowed native submit and uncaught error is mirrored in — so a "the page refreshed on
its own" report is diagnosable after the fact (crumb present = graceful reload with a named cause;
no crumb = engine crash-reload) — ask for it in the next "the app is acting up" report. Transition
note: an already-installed stale app must be fully relaunched once (or re-added) to pick the new
lifecycle up; from then on every deploy self-corrects at the next launch or foregrounding. **v5
(same day — the live report survived v4):** a fresh add still WHITE-SCREENED its first launch (an
intercepted navigation that never produced a document — on a charcoal-dark-default site, white means
NO document rendered) and every uncached tab died the same way, in BOTH the v3 `fetch(e.request)`
and v4 fetch-by-URL forms, while Safari on the same phone was fine: **the SW's OWN network path is
unreliable inside iOS home-screen containers** (which iOS seeds from Safari's state at add-time —
why a pre-add Safari refresh made the front page work: its skeleton was the one thing cached, and
cache-hit serving is the one path that never broke). sw v5 therefore **never intercepts what it does
not positively hold**: a SYNCHRONOUS known-cached gate (`known`, a Set of exact cache-key URLs
primed at worker startup and maintained on every put/evict) decides inside the fetch handler; an
unknown URL is never respondWith'd at all — fully native, so a worker defect can cost an
optimization, never a page. Skeletons are primed in `activate` (background, failure-tolerant); the
versioned shell assets are primed via an **`mc-prime` message from nav.js** (which alone knows the
deploy's `?v=` keys; older same-basename cache entries are evicted as new keys arrive). If a
container's SW networking is truly dead, every priming fetch fails silently and the installed app
simply runs NATIVE forever — browser-identical, never broken. The `?debug=1` overlay also
**auto-shows in standalone when an uncaught error is captured — but ONLY for admins (the `mc-admin`
localStorage flag) since 2026-08-03**, after a regular reader opening Feed met the panel over an
opaque cross-origin "Script error." (which is now recorded but never pops it, for anyone); members
only ever see the overlay by deliberately opening `?debug=1`, which stays available to all because
that screenshot is how their reports get diagnosed. Proven headless 8/8 (`scratchpad/pwa_test2.py`):
no spurious first-install reload, activate-priming, mc-prime, stale-launch auto-heal, VERSION-update
heal + sweep. **Closing finding (same day): the "tabs render shell only, no content" symptom was
ultimately NOT the SW at all** — the Home FOUT gate (`html.mc-home-boot`, added by the inline
`mc-fout` head script on index loads and deliberately persistent on a healthy Home) survived every
soft swap because `<html>` is never swapped, so after launching from Home EVERY soft-navigated page
rendered its content into `main` under the gate's `> :not(mc-home) {display:none}` — DOM complete,
screen empty, zero console errors, cured by a hard refresh (fresh `<html>`), and hit on every
installed-app session because start_url IS Home. Found by diffing ancestor classes between the
broken and working DOM states headless (the join UI was byte-identical in both; only the `<html>`
class differed). Fix: `boots()` in `app/shell.ts` clears `mc-home-boot` on every swap (Home's own
hiding is re-applied per-entry by `mountHome`'s `main.mc-app-home`); verified live on prod across
feed/community/the-book. The lesson for future gates: any page-scoped state stamped on
`<html>`/`<body>` MUST be cleared by the shell on navigation, since only `<main>` is swapped.

clear stamp) — `liked_a`/`liked_b` metadata on the `dms` row beside `opened_at` (**migration

**renumbered `0011_profile_calls_pref.sql` on 2026-09-09** — the file renamed AND the

## Cloudflare Workers (dynamic backend)

**Both workers are TypeScript now (Phase 2D, 2026-08-01).** `comments-worker/src/index.ts` and
`contact-worker/src/index.ts` (wrangler `main` points at the `.ts`; wrangler's esbuild bundles them,
CSP-clean). Each worker has its OWN `tsconfig.json` (Cloudflare Worker globals via
`@cloudflare/workers-types`, `lib: ES2022` — NOT the browser DOM the client tsconfig uses; the two
lib sets conflict, so they are separate projects). `npm run tsc` (part of `make jscheck`)
strict-checks all three projects (client + both workers). `env` is typed by an `interface Env` in
each. The still-JS `comments-worker/src/{pure,webpush}.js` stay `.js` (linted by eslint, imported as
`any`) and remain unit-tested in plain Node; `index.ts` is dropped from the eslint list (tsc covers
it). A worker source change should keep the `wrangler deploy --dry-run` bundle behavior-identical
(type edits erase to the same bytes) — the byte-parity check that gated 2D.

**The comments worker is a MODULE SET now, not a monolith (Phase 3–4, 2026-08-01).** The old
6,381-line `index.ts` was split — each split proven behavior-neutral (tsc-clean + the `wrangler
deploy --dry-run` bundle's function-set and code line-set unchanged bar cosmetic esbuild renames,
live suites green): **`lib.ts`** (the shared core — constants, crypto, auth/validation,
DB/notification/broadcast helpers; a clean leaf that references no handler, imported by everything),
**`durable.ts`** (the two Durable Objects `BoardHub`/`ChatRoom`; index.ts re-exports them via
`import {…}; export {…}` so wrangler finds them on the main module), **`db.ts`** (the repository
layer — typed row mappers `rankFor`/`withNames`/`postCountsFor`, the `inList()` `?N` helper, the
`Query` builder; unit-tested in `tests/worker/db.test.mjs`), and **`index.ts`** itself (the 95
handlers + the **declarative `ROUTES` table** that replaced the 91-branch `if`-chain +
`fetch`/`scheduled`). The keyed-request preamble (parse → rate-limit → key+hash → block-gate) is
single-sourced in the **`keyed`/`keyedGated`** middleware in index.ts. **Gotcha (esbuild + Durable
Objects):** a lib helper reachable ONLY through a re-exported DO's methods gets tree-shaken (esbuild
can't see that Cloudflare calls the DO methods at runtime), which blocks naively extracting handler
groups whose helpers the DO shares into `routes/*` files — verify any further worker split with the
bundle function-set check (`esbuild … --metafile` or grep the dry-run bundle for critical logic),
not tsc alone. Standing verification net for worker changes: `webtest/test_worker_reads.py` (29
read-surface checks) alongside `webtest/test_interactive.py` (24 live-write checks).
