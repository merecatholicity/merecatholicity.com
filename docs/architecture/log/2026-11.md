## Build system

- **The corpus sweeps know pandoc by its prefix, so a current pandoc builds the same site
  (2026-11-04)** — the dev box moved to Arch, whose pandoc 3.11 writes `<meta name="generator"
  content="pandoc 3.11">` where the runner's Ubuntu pandoc writes `content="pandoc"`.
  `page_meta.py` and `split_volumes.py` recognised a pandoc page by the exact second form, so on
  the new box neither touched a single corpus page: 232 pages kept every division as an `<h1>`,
  no oversized volume was split, and `make tests` went red on the sweep's own guard
  (`test_every_page_has_exactly_one_h1`). Both now match `content="pandoc` and a space or quote;
  each has a test with the versioned string. The fresh-clone recipe in the README also gained
  CI's order: `make logos content` before `make html`, which on a clean tree otherwise dies in
  `library-order` reaching for a `library.html` nothing has written yet.

## Cloudflare Workers (dynamic backend)

- **An account hash on the wire now names nobody: resolveId's raw-hash tolerance is retired
  (2026-11-04)** — since the L3 flip (2026-09-18) `resolveId` answered an id missing from the
  reverse map by looking it up as a raw `profiles.hash`, a one-deploy courtesy to old `?u=<hash>`
  links that also served as the net for a member registered after the isolate built its map. Two
  things kept it alive past two due dates. The net needed a replacement, and about twenty call
  sites wrote `(await resolveId(env, x)) || x`, so even without the lookup an unresolved raw hash
  rode straight through to the handler. A miss now tops the map up from the `profiles` rows made
  since it was built (`rowid > _revRowid`: one read, as the lookup was, never a write), and every
  call site answers an unresolved id with `''`, which each handler already refuses. `dmThreadFor`
  takes the wire id from every caller and answers an unknown one with no conversation; the board
  search filters an unknown author to nothing, not to everyone. The retirement found one real bug:
  `/dm/members` resolved its ids, then handed the account hashes to `dmEligible`, which resolves
  again. That worked only because the tolerance resolved an account hash to itself, and without it
  adding a member to a group failed for everyone. It now hands `dmEligible` the wire ids. The sweep
  (`tests/_support/sweep.ts`) sends pubids as a real client does (`wire()`), since raw hashes would
  have stopped at "no such member" and left the egress unread; the reach floors hold unchanged.
  `pubid_roundtrip.test.ts` proves the top-up, the refusal and the group add.

## The PureScript application layer

- **A thread showed twice for an admin: a lazy view mounted once for every route that called it, and
  every admin's boot routed twice (2026-11-04)** — live on the owner's screen,
  `community.html?topic=227#comment-227` drew the crumb, the head, the watch line and the opening
  post twice, with two reply forms, and the fingerprint drawer on the first copy only
  (`annotateMeta` finds a post with `getElementById`, which answers the first of two equal ids). A
  refresh repeated it; leaving for Community and coming back cured it. Two defects met. **The
  trigger**: the pre-load admin hint was `ADMIN_HASHES.indexOf(state.myHash)`, but that list holds
  ACCOUNT hashes and `myHash` has been the PUBLIC id since the P0 chain (2026-09-19), so it never
  matched. Every admin's boot read "not an admin" until `/profile` landed, saw the answer change,
  and called `route()` again: a full redraw on every platform page an admin opened, unseen when both
  runs fell in one task, a rebuild a moment later when the profile came over the network. **The
  bug**: `topic` is one of the four lazy view modules (`app/shell.ts` LAZY_VIEWS, 2026-09-18), and
  its stub mounted for every call made while the chunk was in flight. The second route cleared a
  still-empty section and called again, so the chunk's arrival mounted two `<mc-topic>`. The refresh
  repeated it because the store's disk tier answers `/profile` in a microtask, ahead of any chunk;
  the hop back cured it because the chunk was in by then, the mount was immediate, and the second
  route cleared the first. The classic road had the same flaw, and worse: `lazyView` drew the
  Activity audit twice whenever the profile answer came from the cache, even with its chunk
  installed, because an installed module still answers a microtask after the redraw. **The rule now:
  a late mount ends as an immediate one would have.** `app/lazyviews.ts` (`installLazyViews`, the
  stubs moved out of the shell) takes a hold on the section for each call and mounts only if the
  hold survived. The hold is a comment node: invisible, and `:empty` ignores it, so the CSS loading
  ring still shows while it waits. A route clears the section, the hold goes with it, and the stale
  call stands down whatever the new route draws. The classic `lazyView` takes the same hold through
  `window.mcHoldSection`, since client/ may not import app/ (`transport.test.ts`). **The hint is now
  the device's last answer**: `state.adminHint`, the `mc-admin` flag `loadMyProfile` already wrote
  for the chrome, read once per boot and dropped by `setKey` along with the public id. A known admin
  no longer redraws; a first visit or a changed answer still does, safely. Proven on prod with a
  throwaway identity (only `/profile` answered `admin:true`, every other keyed call answered
  locally, sockets stubbed, the service worker bypassed): the live bundle mounted the thread twice
  on a hard load and on a refresh, and the audit twice both ways. The fixed bundle, served in its
  place, mounted each once in every case, with the redraw forced as well.
  `tests/js/lazy_mount.test.ts` runs the stubs through the race and keeps `lazyView` on the hold;
  `identity_two_names` bars the hint's lookup. **Still broken the same way, not fixed here**: the
  "(admin)" mark on a forum post (`app/views/post.ts`) and on a feed post (`client/wall.ts`) looks a
  row's `author_hash`, a public id, up in the same account-hash list, so it has shown for nobody
  since 2026-09-19. Marking an admin's rows needs the worker to say so.
